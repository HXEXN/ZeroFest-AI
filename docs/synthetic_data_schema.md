# ZeroFest 합성 데이터 구성

`scripts/generate_synthetic_festival_data.py`는 분석과 MVP 시연을 위한 합성 데이터만 생성한다. 실제 판매 데이터로 표시하거나 성능 근거로 사용하지 않는다.

설계 근거와 검증 결과는 [ZeroFest 합성데이터 설계근거 보고서](../outputs/ZeroFest_합성데이터_설계근거_보고서.docx)에 정리했다.

## 변수 선정 근거

### 주문 단위 관측

베이커리 분석의 1위 변수인 고객 티켓 수를 쓰려면 주문 건수가 판매량과 별개로 관측되어야 한다.

**생성 쪽.** 분당 수요를 포아송 한 번으로 뽑지 않고, 먼저 방문 팀 수를 뽑은 뒤 팀마다 구매 수량을 뽑아 합한다. 팀 규모는 공연 단계에 따라 달라진다(`normal` 1.00 → `main_stage` 1.25). 판매량을 상수로 나눠 티켓 수를 만들면 그 변수는 판매량의 재서술일 뿐 독자적인 정보가 없다.

**수집 쪽.** 운영 화면의 `1·2·3·5개 주문` 버튼은 한 번 누르면 **한 팀의 주문**이다. 판매량·재고·주문 건수가 한 번의 입력으로 함께 기록되므로 운영자 부담은 늘지 않는다.

`booth_unique_menu_count_1m`은 데이터셋에만 둔다. MVP 운영 DB는 부스당 메뉴가 1개여서 이 값이 항상 1이 되기 때문이다.


초 단위 이벤트와 초 단위 부스 상태는 감사와 재고 변화 추적에 사용한다. 1분 스냅샷은 운영 화면과 실시간 재예측용 관측 테이블이며, 30분 스냅샷은 안정적인 수요 예측 모델 학습용 피처 테이블이다.

## 축제 진행과 공연 편성

축제는 매일 16:00–22:00, 총 360분간 운영한다. 공연 편성은 개장 이후 경과 분으로 정의한다.

| 구간 | 경과 분 | 시각 | 수요 배수 |
| --- | --- | --- | --- |
| `pre_stage` | 60–119 | 17:00–18:00 | 1.10 |
| `main_stage` | 120–239 | 18:00–20:00 | 1.22 |
| `after_stage` | 240–299 | 20:00–21:00 | 0.95 |
| `normal` | 그 외 | 16–17시, 21–22시 | 1.00 |

`event_ending_soon`은 메인 공연 종료 60분 전 구간(경과 180–239분)이다. 경과 분과 하루 중 분(minute of day)을 혼용하면 모든 공연 구간이 조용히 비활성화되므로, 두 시간 축을 섞지 않는다.

## 재고 준비량

초기 재고는 독립적으로 뽑지 않고 기대 수요에서 역산한다. 메뉴별 3일 평균 기대 수요를 구한 뒤 준비율 `stock_coverage ~ U(0.85, 1.45)`를 곱한다. 준비율이 1.0을 사이에 두고 분포하므로 품절과 잔여재고가 같은 데이터 안에 함께 나타난다. 재고가 항상 부족하면 폐기 데이터가 없어 폐기예측 모델을 학습할 수 없고, 항상 남으면 품절 위험을 학습할 수 없다.

## 날씨

날씨는 부스의 속성이 아니라 축제의 속성이므로 (일자, 분)마다 한 번만 추출해 모든 부스가 공유한다. 3일 축제는 강수일을 독립 추출하기에 너무 짧아, 강수일 수를 먼저 층화 추출(0~2일)한 뒤 해당 일자를 무작위 배정한다.

기온은 일자별 기준 기온에 저녁 냉각 추세와 AR(1) 잡음을 더해 만든다. 기온을 시각의 결정론적 함수로 만들면 기온 변수가 사실상 시계의 별칭이 되어, 모델이 날씨에서 얻는 정보가 시간대 정보의 중복이 된다.

## 할인 배정

할인은 재고나 판매 상태를 보고 발동하지 않는다. 상태를 보고 발동하는 할인은 그 할인을 유발한 위험과 교란되어 효과를 식별할 수 없다.

**블록 무작위 배정.** 메뉴마다 3일 중 1~2일을 배정일로 뽑는다. 모든 메뉴가 두 군에 모두 나타나므로 부스·메뉴 인기도가 메뉴 안에서 상쇄된다. 배정일에는 18:00 이후 30분 블록마다 40% 확률로 할인을 켜고 끄며, 할인율은 메뉴-일마다 10·20·30% 중 하나로 고정한다.

**켜고 끄는 이유.** 한 번 켜서 끝까지 유지하면 할인이 적용된 관측 대부분에서 `recent_sales_30m`이 이미 할인 효과를 담고 있다. 그러면 모델은 할인을 최근 판매량과 중복된 변수로 배우고, "지금 할인하면 어떻게 되는가"에 답하지 못한다. 블록을 켜는 순간(`discount_elapsed_minutes = 0`)의 관측만이 개입 효과를 식별한다.

`discount_elapsed_minutes`는 현재 연속 할인 구간이 시작된 뒤 경과한 분이다. 모델은 이 값이 30분 미만인 할인을 `new_discount_rate`로 분리해 입력받는다.

배정이 균형을 이루는지는 할인이 시작될 수 없는 초반 구간에서 두 군의 잠재 수요 비로 확인한다.

## 타깃과 누수 방지

기본 수요 타깃은 `next_30m_sales_qty`다. 각 스냅샷 시각 이후 1분부터 30분까지의 판매 합계로 만든다. 따라서 `recent_sales_30m`과 시점이 겹치지 않는다.

행사 전 모델은 메뉴 가격, 초기 재고, 위치, 날씨 예보, 공연 편성과 같은 사전 확정 변수만 사용한다. 행사 중 모델은 해당 시점까지의 누적 판매, 최근 판매량, 현재 재고와 승인된 할인만 추가한다. 최종 매출, 최종 티켓 수, 종료 시점 잔여재고는 타깃 또는 사후 평가값이며 입력에서 제외한다.

베이커리 상관분석에서 확인한 가격, 시간대, 티켓 수, 판매 품목 수는 각각 `price_krw`, `hour`, `recent_tickets_30m`, `booth_unique_menu_count_1m`으로 기록한다. 티켓 수는 행사 중 해당 시점까지 관측된 값으로만 재예측에 사용하며 모델 피처에 포함한다. 품목 수는 MVP 운영 DB가 부스당 메뉴 1개라 상수가 되므로 데이터셋에만 둔다.

## 수요 검열 처리

판매량은 수요가 아니라 검열된 수요다. 재고가 0이 되는 순간부터 관측 판매량은 학생이 원한 양을 더 이상 추적하지 않는다.

- `stockout_flag`: 예측 시점의 재고가 0인 관측치
- `censored_window_flag`: 타깃 30분 구간 안에서 재고가 소진되어 타깃이 잘린 관측치
- `next_30m_latent_qty`: 재고 제약을 적용하지 않은 잠재 수요. 합성 데이터이기 때문에만 존재하며, 모델 입력으로 절대 쓰지 않고 검열 편향을 정량화하는 데에만 쓴다

학습과 평가는 `censored_window_flag == 0` 행만 사용한다(`models.demand_model.uncensored`). 검열 행을 그대로 학습하면 이미 품절된 부스에서 수요가 0이라고 예측하도록 배우게 된다.

## 메뉴 구성

카탈로그는 유형별 3종씩 총 9종이다.

| 유형 | 메뉴 (가격) |
| --- | --- |
| food | 닭꼬치 6,000 · 떡볶이 5,000 · 핫도그 4,500 |
| drink | 아이스티 3,500 · 에이드 4,000 · 커피 3,000 |
| dessert | 와플 4,500 · 츄러스 4,000 · 쿠키 3,000 |

부스의 메뉴 유형은 `(부스 번호 + 메뉴 번호) % 3`으로, 유형 안의 품목은 **부스 번호로** 고른다. 두 선택에 같은 인덱스를 쓰면 각 유형이 한 품목에 고정되어 9종 중 3종만 생성되고, 가격이 메뉴 유형의 완전한 재서술이 된다(r=-0.979). 인덱스를 분리하면 유형 안에서 가격이 달라진다(r=-0.705).

가격은 모델 피처가 아니다. 9종을 모두 생성한 뒤에도 기여가 없기 때문이다(중요도 0.004). 수요를 움직이는 것은 가격이 아니라 메뉴별 인기도(`menu_factor`)이며, 가격 변화의 효과는 `discount_rate`가 담는다.

## 합성 규칙

분당 잠재 수요는 메뉴·부스 인기도, 축제 일차, 시간대, 공연 단계, 날씨, 온도, 할인율 및 무작위 변동으로 만든다. Kaggle French Bakery Daily Sales에서 분석한 시간대 판매 분포, 티켓당 수량, 단가 분포를 수요 생성 규칙의 보정값으로 사용한다. 실제 판매량은 잠재 수요와 현재 재고 중 작은 값이다. 이 제약으로 품절, 할인, 재고 소진 시점이 일관되게 연결된다.

기준 분당 수요 `BASE_MINUTE_DEMAND = 0.55`는 메뉴 하나가 6시간 동안 150~250개 팔리는 규모에 맞춘 값이다.

`--profile mvp`는 12개 부스와 부스당 4개 메뉴를 생성한다. `--profile full`은 30개 부스와 부스당 8개 메뉴를 생성한다.

## 연도·캠퍼스 구성

`scripts/prepare_final_training_data.py`는 3개 연도 × 3개 캠퍼스 = 9개 칸을 각각 **서로 다른 시드로 독립 생성**한다. 캠퍼스 규모와 연도 성장률은 시뮬레이션 내부의 수요 배수(`demand_scale`)로 들어가므로 준비 재고도 함께 반응한다.

하나의 실행 결과를 복사해 타깃만 스칼라 배하면, 검증 연도가 학습 연도의 결정론적 변환이 되어 "작년 행을 복사해 1.035를 곱하는" 규칙만으로 R² 1.000이 나온다. 그런 분할의 성능 수치는 일반화와 무관하다.
